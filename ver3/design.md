# Проектирование DSL для SVG Viewer (для непрограммистов)

## Проблема текущего подхода
Сейчас для добавления новой функции (например, "подсвечивать фигуру при клике") непрограммисту (аналитику, тестировщику, заказчику) нужно:
1. Понимать синтаксис JavaScript (скобки, замыкания, `this`, `async/await`).
2. Знать, как работает DOM (`document.getElementById`, `createElement`).
3. Разбираться в CSS (`flex`, `grid`, `overflow`), чтобы ничего не сломать визуально.

Это создает высокий порог входа и риск ошибок.

## Решение: Domain-Specific Language (DSL)
Необходимо создать декларативный язык конфигурации (например, на базе YAML или упрощенного JSON), который описывает **ЧТО** должно делать приложение, а не **КАК** оно это делает. Движок приложения (интерпретатор) будет читать этот файл и сам строить JS/CSS.

### Пример DSL-конфигурации (псевдокод)

```yaml
app:
  name: "SVG Viewer"
  
# 1. Описание макета без CSS-математики
layout:
  - panel: "filelist"
    position: "left"
  - panel: "properties"
    position: "right-top"
    scrollable: true
    sticky_header: true  # Заголовок всегда виден
  - panel: "diagram"
    position: "right-bottom"
  - panel: "log"
    position: "bottom"
    resizable: "top-edge" # Изменение размера за верхнюю границу
    single_line: true     # Лог в одну строку без пропусков

# 2. Источники данных
data:
  files:
    - "https://example.com/diagram1.svg"
    - "https://example.com/diagram2.svg"

# 3. Бизнес-правила (События и действия) на понятном языке
rules:
  - name: "При выборе файла"
    trigger: "click on filelist"
    actions:
      - log: "Пользователь выбрал файл {selected_file}"
      - load_svg: "{selected_file}"
      - extract_shapes: ["rect", "circle", "path", "g"]
      - show_in: "properties"
      - show_in: "diagram"

  - name: "При клике на диаграмму без выбора"
    trigger: "click on diagram"
    condition: "selected_file is empty"
    actions:
      - log: "Ошибка: Сначала выберите файл в списке"
```

## Преимущества такого подхода для непрограммиста:
1. **Отсутствие деталей реализации**: Нет упоминаний `div`, `addEventListener`, `fetch`, `#eee` или `flex-shrink: 0`. Цвета, отступы и сетки скрыты внутри движка.
2. **Читаемость**: Правила читаются как обычный текст на русском/английском языке (`trigger`, `actions`).
3. **Безопасность изменений**: Невозможно случайно удалить закрывающую скобку `}` или точку с запятой `;`, что приводит к падению всего JS-скрипта. YAML-валидатор сразу укажет на ошибку структуры.
4. **Легкость доработки**: Чтобы добавить новое действие (например, "отправить лог на сервер"), достаточно добавить одну строку `- send_log_to: "https://api.myserver.com/log"`, не вникая в то, как работает `XMLHttpRequest` или `fetch`.

## Как это реализовать технически (Архитектура интерпретатора):
1. Создается файл `engine.js` (ядро), который знает, как рендерить стандартные панели и обрабатывать стандартные действия.
2. Создается файл `rules.yaml` (или `rules.json`), который пишет аналитик.
3. При запуске `engine.js` читает `rules.yaml`, динамически генерирует HTML-структуру, навешивает обработчики событий и выполняет действия, описанные в правилах.
4. Текущий `app.js` будет полностью удален или сильно сокращен до роли этого самого "движка", а вся логика переедет в текстовый конфигурационный файл.
