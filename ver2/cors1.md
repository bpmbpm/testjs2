## 1

Тут есть важный нюанс: **«работает при двойном клике» и «работает на GitHub Pages» — это два разных режима**, и CORS‑проблемы в них ведут себя по‑разному.

## В чём разница

| Сценарий | Откуда грузятся файлы | Политика браузера | Что происходит с `fetch` |
|---|---|---|---|
| **Двойной клик по `index.html`** | Протокол `file://` (локальный диск) | Браузер считает это «без источника» (`null origin`). Любые запросы к другим файлам (даже в той же папке) считаются кросс‑доменными. | `fetch` блокируется CORS. Ошибка: `Failed to fetch`. |
| **GitHub Pages** | Протокол `https://` (сайт) | У всех файлов один и тот же origin (домен GitHub Pages). | CORS разрешает `fetch` между файлами сайта. Всё работает. |
| **Локальный сервер** (`Live Server`, `python -m http.server`) | Протокол `http://127.0.0.1` | У всех файлов одинаковый origin (localhost). | CORS разрешает `fetch`. Всё работает. |

## Почему у тебя «всё работает» при двойном клике

Есть три вероятные причины, почему ты не видишь ошибки:

1. **Ты на самом деле запускаешь через Live Server / локальный сервер**, а не двойным кликом. В VS Code кнопка «Open with Live Server» — это не двойной клик, это запуск HTTP‑сервера.
2. **SVG подгружаются не через `fetch`, а как `<img src="...">`**. Если SVG вставлены через тег `<img>`, браузер не применяет к ним CORS так строго, как к `fetch`. Но в твоём коде используется именно `fetch` + `DOMParser`, поэтому для него CORS критичен.
3. **Консоль не открыта или логирование заглушено**. Ошибка `TypeError: Failed to fetch` появляется только в консоли браузера (F12). Если её не смотреть — кажется, что «ничего не происходит».

---

## Что значит «обход CORS через обёртку config.js»

Обёртка в `config.js` (где ты объявляешь `window.svgFileList = [...]`) **не обходит CORS**. Она просто задаёт список URL, откуда потом пойдёт `fetch`. Сама по себе инициализация переменной не делает запросы. CORS проверяется именно в момент `fetch(url)`.

Размещение SVG на GitHub Pages помогает только в одном случае: если ты открываешь свой `index.html` **тоже с GitHub Pages** (т.е. сайт целиком хостится там). Тогда и `index.html`, и SVG имеют один origin — CORS разрешает запрос.

Но если ты **локально открываешь свой `index.html` через двойной клик**, а в нём прописаны ссылки на SVG с GitHub Pages, то браузер видит:
* origin страницы: `file://` (null)
* origin запроса: `https://github.io`

Это разные origin → CORS блокирует `fetch`.

## Важный нюанс про «локально всё работает»

Иногда при двойном клике браузеры (особенно Chrome) могут загружать локальные файлы из той же папки без CORS‑ошибок, потому что это «особые случаи» для `file://`. Но:

- Это **нестандартное поведение**.
- Оно **не гарантируется** и может меняться с обновлениями браузера.
- Оно **не работает** для запросов на другие домены (GitHub Pages и т. п.).

Поэтому для разработки и тестирования `fetch` всегда нужно использовать **HTTP‑сервер** (Live Server, `python -m http.server` и т. д.). Тогда поведение будет одинаковым и на локальной машине, и на GitHub Pages.

Если положить SVG в ту же папку и использовать относительные пути, то при запуске с локального сервера всё будет работать. На GitHub Pages ты можешь положить те же файлы рядом — и поведение останется одинаковым.

## Почему у тебя сработало (и это обманчиво)

Есть три возможных объяснения, почему `fetch` к GitHub Pages сработал при открытии локального `index.html`:

1. **Ты на самом деле запустил через Live Server, а не двойным кликом.**  
   В VS Code кнопка «Open with Live Server» выглядит как «запуск файла», но технически это **HTTP‑сервер** (`http://127.0.0.1:5500`). Браузер видит origin страницы как `127.0.0.1`, а GitHub Pages — как `github.io`. Это **разные origin**, и CORS должен блокировать запрос. Но… иногда браузеры (особенно Chrome в dev‑режиме или с флагами) могут вести себя нестандартно, либо GitHub Pages отдаёт заголовки, которые временно «пропускают» запросы. Это **не гарантированное поведение**.
2. **SVG-файл на GitHub Pages имеет CORS‑заголовки, разрешающие любые запросы.**  
   Иногда GitHub Pages (или прокси перед ним) отдаёт заголовок `Access-Control-Allow-Origin: *`. Если это так, то даже при `file://` или `localhost` запрос пройдёт. Но это **настройка сервера**, а не правило браузера. Если завтра GitHub изменит политику или ты положишь SVG на другой хостинг — всё сломается.
3. **Кэш и старые файлы.**  
   Браузер мог закэшировать SVG‑файл ранее (когда ты открывал страницу с GitHub Pages), и сейчас он просто достал его из кэша, не делая реального сетевого запроса. Тогда `fetch` вернул закэшированный ответ без проверки CORS.

> **Ключевой момент:** Если ты открыл `index.html` именно двойным кликом (адрес в строке начинается с `file:///C:/Users/...`), то по строгой спецификации браузера запрос к `github.io` **обязан быть заблокирован**. Тот факт, что он прошёл, — это исключение, а не правило.

| **Твой текущий (локальный `index.html` + GitHub SVG)** | `file://` или `http://localhost` | `https://github.io` | Разные origin → CORS блокирует (по стандарту) | ❌ Нестабильно, может сломаться в любой момент |
| **GitHub Pages для всего (и `index.html`, и SVG)** | `https://github.io` | `https://github.io` | Один origin → CORS разрешает | ✅ **Гарантированно работает** |
| **Локальный сервер + локальные SVG** | `http://127.0.0.1` | `http://127.0.0.1` | Один origin → CORS разрешает | ✅ Работает локально, но не на GitHub |

Именно поэтому в продакшене и при демонстрации проекта **нельзя полагаться на то, что «у меня на ПК всё работает»**. Нужно, чтобы проект работал в стандартизированных условиях.

## Что происходит «под капотом»

### 1. GitHub Pages отдаёт заголовок `Access-Control-Allow-Origin: *`
Это самая вероятная причина. GitHub Pages (как и многие CDN) для статических файлов по умолчанию ставит заголовок:
```http
Access-Control-Allow-Origin: *
```
Что это значит: «Я разрешаю читать эти файлы через `fetch` с любого сайта, даже с `file://`».

**Как это обходит CORS:**
- Браузер видит: запрос с `file://` на `github.io`. Это разные origin → CORS должен сработать.
- Но сервер (`github.io`) в ответе присылает: `Access-Control-Allow-Origin: *`.
- Браузер читает этот заголовок и говорит: «Сервер явно разрешил, значит, я отдам данные JS‑коду».
- `fetch` завершается успешно, и твой код видит `SVG успешно загружен`.

Именно поэтому твой код работает даже при двойном клике. Сервер сам «открыл дверь».

---

### 2. Почему я говорил про «единственный гарантированный вариант»

Я настаивал на том, чтобы и `index.html`, и SVG лежали на GitHub Pages, потому что **заголовок `Access-Control-Allow-Origin: *` — это не гарантия**.

Вот где могут быть сюрпризы:

- **Ты можешь положить SVG на другой хостинг.** Например, на S3, свой сервер или корпоративный CDN. Там по умолчанию такого заголовка нет. И тогда при запуске с `file://` запрос сразу сломается.
- **GitHub может поменять политику.** Сегодня они отдают `*`, завтра решат, что для безопасности будут отдавать только конкретный origin или вообще уберут заголовок. Твой код перестанет работать у всех, кто открывает файл локально.
- **Корпоративные браузеры и политики.** В некоторых компаниях браузеры настроены так, что игнорируют `Access-Control-Allow-Origin: *` для протокола `file://`, считая его слишком опасным. В офисе твой проект покажет ошибку, хотя дома всё работало.
- **Разные браузеры.** Edge, Firefox, Safari могут строже проверять CORS для `file://`, чем Chrome. То, что работает в Chrome, может не работать в другом браузере.

Поэтому правило «один origin = нет проблем с CORS» — это **единственный способ, который не зависит от настроек сервера и браузера**. Если страница и файлы лежат на `github.io`, браузеру вообще не нужно проверять CORS, потому что origin одинаковый. Это работает всегда.
